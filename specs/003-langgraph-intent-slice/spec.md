## User Scenarios & Testing *(mandatory)*

### User Story 1 - Classify and Route Chat Intent (Priority: P1)

As a user, my message is classified into a known intent category so the system can route it consistently and expose the routing decision for debugging.

**Why this priority**: Correct routing is the backbone of this slice and is required before generating capability-specific responses.

**Independent Test**: Send messages representing each category and verify intent classification is visible in stream output, and routing behavior matches this pass scope.

**Acceptance Scenarios**:

1. **Given** an incoming chat message, **When** the classify intent step runs, **Then** the message is labeled as one of: policy_question, action_request, direct_response, escalation, or blocked.
2. **Given** a message classified as policy_question, action_request, escalation, or blocked, **When** response generation runs, **Then** the system returns the exact placeholder response `This type of request isn't supported yet.`.
3. **Given** any classified message, **When** streaming response events, **Then** the chosen intent is emitted in a dedicated `intent` SSE event before any response token events.

---

### User Story 2 - Generate Real Direct Responses Through LangGraph (Priority: P1)

As a user asking general IT small-talk or non-policy questions, I receive a real conversational response generated by the LLM instead of a hardcoded response.

**Why this priority**: This is the main value of the second vertical slice and replaces the previous hardcoded response path.

**Independent Test**: Send a direct-response-style message and verify streamed output reflects real LLM-generated content routed through LangGraph.

**Acceptance Scenarios**:

1. **Given** a message classified as direct_response, **When** the generate response step runs, **Then** the system calls the LLM and produces a real conversational answer.
2. **Given** a direct_response request, **When** output is streamed via /chat/stream, **Then** the existing SSE contract is preserved while streaming the generated response.
3. **Given** a direct_response message where LLM generation fails, **When** response generation handles the failure, **Then** the stream emits an `error` event and stops without placeholder fallback text.
4. **Given** a successful direct_response or placeholder non-direct flow, **When** streaming events are emitted, **Then** sequence is `intent` first, followed by one or more `token` events, followed by exactly one terminal `done` event.

---

### User Story 3 - Preserve Stage-1 Reliability Contracts (Priority: P2)

As a platform owner, I need all existing validation, error shape, and disconnect guarantees to remain unchanged while adding intent and LangGraph flow.

**Why this priority**: Expanding capability must not regress established API reliability behavior.

**Independent Test**: Run all existing stage-1 validation/error/disconnect tests unchanged and confirm they continue to pass.

**Acceptance Scenarios**:

1. **Given** missing, empty, or whitespace-only required fields, **When** /chat/stream is called, **Then** the response remains HTTP 422 with error code ERR-VALIDATION-MISSING-FIELD and the established error shape.
2. **Given** a client disconnect during streaming, **When** generation is in progress, **Then** the server stops generation immediately with no retry and no further events.
3. **Given** the second-slice intent flow is enabled, **When** existing stage-1 tests are executed, **Then** they pass without requiring contract changes.

### Edge Cases

- A direct_response classification must not accidentally return the placeholder unsupported response.
- Non-direct intents still classify correctly even though their capability outputs are placeholders in this pass.
- Intent visibility data must be present even when the final response is the unsupported placeholder.
- Disconnect handling must stop in-flight LLM generation with no post-disconnect events.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST introduce a LangGraph state graph for chat flow orchestration.
- **FR-002**: System MUST define an AgentState containing at minimum user_id, session_id, message, intent, and response.
- **FR-003**: System MUST include a classify_intent node that classifies incoming messages into exactly one of: policy_question, action_request, direct_response, escalation, blocked.
- **FR-004**: System MUST include a generate_response node that handles direct_response intent by calling the LLM for a real conversational answer.
- **FR-004A**: If direct_response LLM generation fails, system MUST emit an SSE `error` event and stop streaming without placeholder fallback text.
- **FR-005**: For policy_question, action_request, escalation, and blocked intents, system MUST return the exact placeholder response `This type of request isn't supported yet.`.
- **FR-006**: System MUST replace the previous hardcoded chat response path with the LangGraph-driven path.
- **FR-007**: System MUST stream responses through the existing /chat/stream SSE mechanism.
- **FR-008**: System MUST preserve the existing /chat/stream contract behavior for validation handling, disconnect handling, and validation error shape, while extending stream event types to include `intent`.
- **FR-009**: System MUST expose intent classification in the SSE stream using a dedicated intent-visibility event emitted before any response token events.
- **FR-009A**: System MUST extend `ChatStreamEvent.event_type` to include `intent` for this slice.
- **FR-009B**: For successful intent paths, stream event order MUST be `intent` first, then one or more `token` events, then exactly one terminal `done` event.
- **FR-009C**: For direct_response LLM failure path, stream event order MUST be `intent` then `error`, after which stream terminates without `done`.
- **FR-010**: System MUST maintain existing validation outcomes for missing, empty, and whitespace-only required fields, including HTTP 422 and ERR-VALIDATION-MISSING-FIELD response semantics.
- **FR-011**: System MUST maintain existing disconnect behavior: immediate stop, no retry, no further events.
- **FR-012**: This pass MUST NOT implement RAG or ChromaDB retrieval.
- **FR-013**: This pass MUST NOT implement FastMCP tools, including ticket status, password reset, or ticket creation actions.
- **FR-014**: This pass MUST NOT implement PII redaction or prompt injection detection.
- **FR-015**: This pass MUST NOT implement long-term memory, Arize Phoenix instrumentation, Promptfoo evaluation, or React frontend.

### Key Entities *(include if feature involves data)*

- **AgentState**: Stateful chat object carrying user_id, session_id, message, intent, and response through LangGraph nodes.
- **Intent Classification**: Routing label selected from policy_question, action_request, direct_response, escalation, blocked.
- **Response Payload**: Final generated or placeholder response text emitted through existing SSE streaming behavior.
- **Intent Visibility Signal**: Dedicated SSE event with `event_type` set to `intent` and data carrying the selected classification.
- **Validation Error Response**: Existing 422 response contract with ERR-VALIDATION-MISSING-FIELD and stable message/details shape.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of acceptance tests for direct_response messages produce an LLM-generated conversational answer streamed through /chat/stream.
- **SC-002**: 100% of acceptance tests for policy_question, action_request, escalation, and blocked classifications return the placeholder unsupported response rather than an internal error.
- **SC-003**: 100% of acceptance tests expose intent classification in stream output for debugging.
- **SC-004**: 100% of previously passing stage-1 validation, error-shape, and disconnect tests continue to pass unchanged.

## Assumptions

- The existing /chat/stream endpoint and schema boundary contracts remain the integration point for this slice.
- An LLM provider configuration is available for the direct_response generation path in environments where acceptance tests run.
- Placeholder responses for non-direct intents are acceptable until their dedicated capabilities are implemented in later slices.
- This slice focuses on routing and direct conversational response only, while deferred capabilities keep their existing out-of-scope status.
